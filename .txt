Title: Password recovery, password changes, and application-session revocation
Date: 2026-10-29
Repo: C:\Users\alvin\OneDrive\Desktop\GitHub_Repos\SOC_BOT

Goal:
- Extend the existing frontend auth Lambda with forgot-password, reset-password, and change-password.
- Revoke all application sessions after a confirmed password update, without storing Cognito tokens.
- Handle partial success honestly using bounded SDK retries and documented manual recovery.

Scope:
- Implement code, CDK permissions/routes, and focused documentation only. Do not deploy, invoke AWS APIs, run workflows, commit, or create/modify/delete tests.
- Preserve the signup slice, login/me/logout, 12-hour fixed sessions, existing origin-header and browser-Origin protections, and environment isolation.
- Do not add Google/linking, MFA, UI, chat authentication cutover, new functions/tables, background workers, retry libraries, or a durable password-operation framework.

Plan:
1) Reconcile the current auth implementation and add strict contracts.
   - Read AGENTS.md, current auth documentation, and the signup implementation before editing. Preserve ongoing changes; report material conflicts rather than silently redesigning them.
   - Work primarily in infra/lambdas/frontend/auth/{contracts,http,handler,errors,cognito,user-state}.ts. Add a focused passwords.ts service for these flows, following registration.ts's organization rather than enlarging handler.ts with provider logic.
   - Add POST /api/auth/forgot-password with {"email":"user@example.com"}.
   - Add POST /api/auth/reset-password with {"email":"user@example.com","code":"012345","newPassword":"..."}.
   - Add POST /api/auth/change-password with {"currentPassword":"...","newPassword":"..."}, plus the existing opaque session cookie.
   - Reject extra fields, client-supplied user IDs, subjects, versions, tokens, and query parameters. Reuse email normalization and the signup password policy: new passwords are 15-256 characters without whitespace. Never trim/change passwords; preserve recovery codes as strings including leading zeroes, using the existing bounded code validation.
   - Do not tighten existing login password validation or change signup responses incidentally.

2) Implement generic password-recovery requests.
   - Use ForgotPassword with the configured no-secret client, not an administrative password-reset operation.
   - Return identical HTTP 202 JSON for accepted and known ineligible/nonexistent accounts:
     {"message":"If this account is eligible for password recovery, check your email for a reset code."}
   - Do not expose delivery destinations, account status, provider messages, or whether a code was actually sent.
   - Follow registration.ts's narrow error-classification pattern. An ambiguous provider error must not turn a broken client/pool configuration or delivery failure into apparent success. Where necessary, use a bounded exact-pool AdminGetUser lookup to distinguish known ineligibility from an operational failure; return safe 429/503 for operational categories.
   - Merely requesting a code must not create USER metadata or sessions, increment session_version, delete sessions, or change cookies.

3) Implement both password-update flows with the correct identity proof.
   - Reset: resolve the normalized email to a canonical local account/subject using trusted provider data, then call ConfirmForgotPassword with its canonical username and the submitted code/new password. Support recovery-eligible CONFIRMED and RESET_REQUIRED users; do not blindly reuse login's helper, which currently rejects RESET_REQUIRED.
   - Code verification remains Cognito's responsibility. Unknown/ineligible accounts and invalid/expired codes receive a common safe reset-failed response, without disclosing account existence.
   - A user may reset a password before ever logging in. Before attempting the mutation, distinguish genuinely missing metadata from malformed metadata using the existing strongly consistent provisioning helpers. For a trusted eligible account only, conditionally initialize a genuinely absent USER record using the existing first-login shape, and reread after a confirmed competing initialization. This is not authentication and must not create a session. Never overwrite existing state, reset an existing version, re-enable disabled users, or treat malformed state as absence.
   - Change: require a valid current BFF session, derive the subject from it, resolve its canonical local username, and freshly authenticate with currentPassword. Verify that the authenticated identity matches the session subject.
   - Obtain the short-lived access token required by ChangePassword through that fresh authentication. Validate the token against the configured pool/client and expected subject, token use/expiry, and required aws.cognito.signin.user.admin scope using existing verification dependencies. Keep it in server memory only, pass it to ChangePassword with PreviousPassword/ProposedPassword, then discard it.
   - Add a focused internal capability for this transient token; do not expose tokens in the existing login result or HTTP responses. No automatic login/session creation, AdminSetUserPassword, AdminResetUserPassword, or account confirmation bypass.
   - Revalidate the original session before change-password mutation if intervening work could make it stale; do not adopt newer metadata to authorize an invalidated session.

4) Add bounded, idempotent application-session revocation.
   - After Cognito CONFIRMS password success, perform a fresh strongly consistent read of that subject's valid USER_AUTH_STATE, then increment session_version. Reuse the permanent metadata schema without TTL, preserving disabled and all identity fields.
   - Use a focused helper in user-state.ts rather than relying on the current retryable ADD-based increment as-is. A single-item TransactWriteCommand with a conditional Update and a stable ClientRequestToken can make SDK retries of the identical update idempotent.
   - Condition on the observed version and expected identity/state shape; set the next safe integer version. Generate the token once and reuse the identical transaction across bounded SDK retries. Do not regenerate a token for an uncertain write or blindly rebuild an increment after an ambiguous failure.
   - Treat confirmed conflicts, missing/malformed metadata, exhausted retries, and unconfirmed writes as revocation-unconfirmed. Do not infer this operation succeeded just because a subsequent read has a higher version: another password operation may have changed it.
   - The post-success read matters: a version change from before this password mutation is not proof that this mutation revoked sessions.
   - Do not scan/delete all session items or wait for TTL. Existing session resolution already rejects stale versions on each protected request. Keep unrelated disable/session helpers unchanged unless a narrow shared adjustment is necessary.

5) Implement explicit success, rejection, partial-success, and uncertain-outcome responses.
   - Full success: HTTP 200 {"message":"Password updated. Sign in again."}, only after both Cognito success and confirmed metadata update. Clear the browser's existing session cookie using the exact current cookie attributes. Do not issue a replacement cookie/session.
   - Provider rejection: invalid code/current password/password policy returns the appropriate safe 400/401; throttling returns safe 429. Do not revoke sessions or clear a valid session just because validation or identity proof failed.
   - Confirmed password success but unconfirmed revocation: HTTP 503 using the existing error envelope, requestId, and a distinct code PASSWORD_CHANGED_SESSION_REVOCATION_UNCONFIRMED. Message:
     "Your password was changed, but signing out existing sessions could not be confirmed. Contact the administrator."
     Clear the current browser cookie, but do not claim that this proves server-side or other-device revocation.
   - Cognito password mutations have no caller idempotency token. Use a dedicated mutation client configuration with maxAttempts: 1 for ConfirmForgotPassword and ChangePassword; keep existing bounded SDK retries for safe reads and identical idempotent DynamoDB transactions. Do not alter other routes' retry settings.
   - Transport timeout/connection loss or an ambiguous provider failure after dispatch must return a distinct safe 503 PASSWORD_UPDATE_UNCONFIRMED, not a claim that the password definitely failed or succeeded. Explain that the user should verify access/request a fresh recovery code or contact the administrator, not blindly repeat a consumed code/old-password mutation. Do not claim sessions were revoked on this path.
   - Preserve the existing request deadline/Lambda/API timeout relationship. Reserve time for post-Cognito revocation and response serialization, cap mutation calls appropriately, and refuse to start a mutation when insufficient budget remains. No unbounded retry loops, timeout increases, or sleeps.
   - Persist no submitted credentials or provider response. Extend existing safe outcome logging with fixed classifications and requestId only; never log emails, subjects, cookie/hash values, passwords, codes, tokens, request bodies, or raw SDK errors. Keep success/partial/uncertain outcomes distinguishable in logs.

6) Wire the existing API and least-privilege IAM.
   - Extend infra/lambdas/frontend/shared/origin-routes.ts, HTTP discriminated request types, and the explicit handler switch with the three hyphenated route names.
   - All three POST routes retain exact API/stage/method validation, JSON/body bounds, browser-Origin/Fetch Metadata checks, no-store responses, and the zero-cache origin-verification authorizer. Only change-password requires a prior BFF session; reset-password uses the recovery code instead.
   - In infra/lib/stacks/frontend/frontend-auth.ts, let the shared route list create exact-method integrations/invoke permissions. Update narrow resource-specific authorization acknowledgments to accurately distinguish recovery from session-protected change-password.
   - Add only dynamodb:UpdateItem on props.table.tableArn to the auth execution role. Confirm the APPLICATION boundary already permits it; do not broaden foundation permissions unnecessarily.
   - Retain exact-pool AdminGetUser. ForgotPassword, ConfirmForgotPassword, and ChangePassword are public/token-authorized Cognito operations that do not evaluate IAM, so do not add fictitious IAM grants or broad cognito-idp:* permissions.
   - Keep current function sizing, resource ownership/names, workflows, CloudFront routing, WAF, and all unrelated policies unchanged.

7) Document operational recovery and the accepted MVP limitation.
   - Update infra/lambdas/frontend/auth/README.md and Docs/FrontendStack/README.md with contracts, response codes, identity proof, cookie behavior, and revocation semantics. Update existing spec summaries only where necessary to remove contradictions, and add the required logs.md entry.
   - Document that Cognito and DynamoDB cannot commit atomically: a password update can succeed while old application sessions remain usable. Clearing a browser cookie does not resolve this server-side risk.
   - Provide a concise administrator runbook: correlate the safe requestId/outcome; independently identify the intended account using trusted administrative tools; inspect valid current USER metadata; complete a conditional, bounded version increment preserving disabled; verify old sessions fail. Do not rerun the Cognito mutation just to complete revocation.
   - A missing/malformed record requires investigation, not a reset to version 1. Never put passwords/codes/session cookies in an issue, log, committed file, or recovery command history.
   - State that automatic durable recovery, Cognito token global sign-out, account-wide disablement workflows, and public-demo abuse controls remain deferred. This slice revokes application sessions, not every Cognito-issued token or other application's sessions.

8) Perform local verification and hand off operator validation.
   - Run the existing lint/build/tests and targeted synthesis as described below, without adding or changing test cases. Review the final diff for accidental signup/auth behavior changes, wildcard grants, secrets, and unrelated files.
   - Report all checks actually run, any failures, remaining assumptions, and synthesized IAM/route changes. If existing tests require an unauthorized test edit, stop and report it.
   - Do not deploy or contact the account. The operator will deploy and validate the flows through CloudFront after review.

Risks/Notes:
- Work starts from the completed signup slice; do not overwrite its implementation or silently roll it back.
- The MVP deliberately accepts the interval/partial-failure risk between Cognito mutation and DynamoDB revocation. Neither generic errors nor cookie clearing may hide that risk.
- Session invalidation is enforced on subsequent protected requests, not as push logout or cancellation of already-authorized in-flight work.
- Account-recovery email delivery requires a verified eligible email and the pool's configured self-service recovery setting. Inspect the existing CDK first; if a required setting is absent, report the narrow prerequisite instead of changing unrelated Cognito configuration.
- SDK transaction idempotency is bounded and request-local, not a new durable cross-request retry contract. Never promise that replaying the HTTP password request is idempotent.
- No new automated tests are authorized for this slice.
