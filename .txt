2) Define and enforce the three HTTP contracts.
   - POST /api/auth/login: application/json body exactly {"email":"analyst@example.com","password":"example-only"}. Return 200 with {"userId":"<verified-cognito-sub>","expiresAt":"<UTC-ISO-8601>"} and the opaque Set-Cookie header only after confirmed session persistence.
   - GET /api/auth/me: no body/query parameters; cookie is the only session input. Return the same 200 userId/expiresAt shape for a valid session. Do not return a raw token, session hash, email/profile data, or session version.
   - POST /api/auth/logout: no query parameters and either an empty body or {}. Require application/json for this POST even when its body is empty. Return 204 with an empty body and a clearing Set-Cookie header only after confirmed current-session deletion, or when no usable cookie exists.
   - Validate REST API proxy event shape, expected API/stage/account, supported exact method/resource pairs, JSON object shape, content type, and bounded decoded body size (8 KiB). Reject unknown fields such as userId, sub, version, or lifetime. Parse base64 safely if present; do not accept forms or credentials in URLs.
   - Validate email consistently with the existing Cognito username limit (128 characters), normalize its surrounding whitespace/case for the case-insensitive pool, and never trim/normalize the password. Preserve the existing 256-character password-input bound; do not impose new-password complexity rules on login.
   - Use safe errors with a stable shape such as {"error":{"code":"AUTHENTICATION_FAILED","message":"Email or password is incorrect."},"requestId":"<request-id>"}.
   - Status mapping: 400 malformed input; 413 oversized body; 415 unsupported media type; 401 denied credentials or absent/invalid/revoked session; 403 invalid origin or unconfirmed account (ACCOUNT_NOT_CONFIRMED); 429 throttling; 503 backend/configuration unavailability. Distinguish unsupported authentication challenges safely without returning Cognito challenge sessions. Never expose raw SDK/JWT errors.
   - Responses, including errors and logout, use Cache-Control: no-store and appropriate safe JSON headers. Never include credentials, cookies, Cognito JWTs/refresh tokens, or raw provider details in JSON.

3) Preserve origin protection and add browser-origin/CSRF checks.
   - Extend the preceding slice's REQUEST authorizer exact allowlist to the existing GET /api/health plus precisely these three routes. Keep authorization-result TTL zero and return permission for only the validated incoming method ARN, not a wildcard.
   - Keep secret fetching/comparison in that authorizer/shared origin guard. The auth Lambda must verify trusted API Gateway authorization context, but needs no additional Secrets Manager grant or duplicate secret fetch.
   - The verified origin principal is not a user identity. Login remains accessible without a session; me/logout resolve the opaque cookie internally. Do not trust a caller-supplied principal/userId or make login require an existing session.
   - Configure the exact allowed browser origin as https://<this-environment-distribution-hostname> using a CDK reference, not viewer Host, X-Forwarded-Host, arbitrary request headers, a wildcard, or the execute-api hostname.
   - Before POST login/logout performs any work, require one unambiguous Origin equal to that configured origin. Reject missing, null, cross-origin, or conflicting values. Require JSON, reject Sec-Fetch-Site: cross-site when supplied, and do not add permissive CORS or Referer fallback. Protect login as well as logout against CSRF.
   - GET me can omit Origin for same-origin GET/manual clients; reject an explicit mismatched/null/ambiguous Origin or cross-site Fetch Metadata. It must not mutate or renew session state.
   - Handle equivalent single/multivalue API Gateway headers correctly while rejecting actual ambiguous duplicates. Preserve strict cookie parsing.
   - Keep CloudFront /api/* cookie/header forwarding and caching disabled, API Gateway response caching off, and no SPA error rewrite. Ensure auth errors are not edge-cached (honor no-store; use zero minimum error TTL for relevant CloudFront-cached API error statuses if necessary, without response remapping).
   - Missing/bad origin-secret requests remain denied before the auth integration. No auth route may be created with AuthorizationType.NONE as a shortcut.

4) Implement trusted login orchestration and narrowly scoped first-login metadata provisioning.
   - Use AdminGetUser against the configured pool with the email alias to obtain the canonical Cognito Username, sub, Enabled flag, and account status. Do not use ListUsers, client-supplied subjects, or a JWT decoded without verification.
   - Only enabled, confirmed local password accounts may proceed. Map absent/disabled users to the same safe credential failure; unconfirmed accounts use the agreed safe 403 code. Temporary-password, reset-required, MFA, or other unsupported challenge states fail closed without implementing those flows.
   - Make trusted first-login provisioning explicit: after the server's canonical account lookup, distinguish genuinely absent USER#sub metadata from existing malformed metadata. Only an absent record can be conditionally initialized to version 1 / disabled false, before password authentication starts.
   - Reuse the existing conditional initialize helper; never replace/reset existing metadata, clear disabled, or adopt defaults for malformed state. If concurrent initialization wins, permit one bounded strong reread before authentication and require valid enabled state. Preserve no-TTL user metadata. Do not initialize state during me/cookie resolution.
   - Capture the process-local TrustedAuthenticationContext through readForAuthentication BEFORE verifying credentials. Authenticate using the canonical server-resolved username with the existing USER_PASSWORD_AUTH adapter, then verify the ID JWT signature, issuer, client, token use, live expiry, and equality of the verified sub to the snapshot.
   - Keep the verified identity and Cognito tokens internal; discard all provider tokens after verification. Refine the adapter's current blanket error handling so transient service/JWKS outages are safe 503s, throttling is 429, and credential failures remain generic, without logging raw causes.
   - Transactionally check the original enabled metadata/version while inserting a freshly generated session. Never reread and adopt a newer version after credential verification or retry the authentication transaction as a fresh snapshot.
   - Keep one stable transaction idempotency token and the same generated session record throughout SDK retries. On an ambiguous persistence result, do not return success or mint another session inside an outer retry loop; an unconfirmed committed session can expire naturally.
   - A submitted cookie never selects the login identity. Mint a fresh opaque token on every successful login; do not globally revoke other device sessions or erase an existing cookie merely because a login attempt failed.
   - This provisioning is a defined first-login path, not proof of the password and not automatic recovery from deleted user state. Document that losing/deleting revocation metadata is an operator recovery issue.

5) Implement me/logout using the existing durable session contract.
   - Keep the existing item shapes: permanent USER#<sub> with entity_type/sub/session_version/disabled; SESSION#<SHA-256-token-hash> with entity_type/sub/session_version/created_at/expires_at. Do not add a GSI, token storage, sliding expiration, profile cache, or a new table.
   - Keep random 32-byte opaque tokens, hash-only DynamoDB keys, and absolute 43,200-second expiry independent of Cognito token expiry. Preserve __Host-soc_bot_session, Secure, HttpOnly, SameSite=Lax, Path=/, no Domain, and persistent Max-Age/Expires aligned to server expiry.
   - me uses strongly consistent session and user-state reads on every request, with schema/key/sub/expiry/disabled/version checks and no authorization cache or Cognito round trip. Invalid/missing sessions return 401; a present invalid cookie may be cleared. Storage failure returns 503, never authenticated or merely logged out.
   - Logout deletes only the cookie-selected SESSION key, then clears the cookie. Missing/malformed cookies clear idempotently; a deletion failure returns 503 without claiming logout succeeded or clearing a usable cookie. Do not increment session_version, call Cognito GlobalSignOut, or require successful me resolution before deleting an expired/revoked session.
   - Reuse AWS SDK retries (maxAttempts 2) with bounded request cancellation and a handler-wide deadline. No Tenacity-style package or outer retry framework. Do not retry denied credentials, validation failures, or conditional-version failures.
   - Bound the complete handler to approximately 20 seconds of work with a 25-second Lambda timeout, reserving time for a safe response. Clamp SDK/JWKS work to the remaining deadline rather than allowing each existing 10-second helper timeout to accumulate beyond it. Use supported verifier/network settings; preserve cryptographic verification.
   - Do not create global recovery/revocation workers or synchronization with out-of-band Cognito console actions. Document that later password/admin flows must update DynamoDB versions to invalidate already established sessions.
