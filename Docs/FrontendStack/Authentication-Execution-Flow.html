Authentication execution flow · Passes 1–3

From password proof
to an owned chat turn.

Follow actual function calls and data shapes: registration and confirmation, password login and opaque sessions, authenticated chat, logout, recovery and password-change revocation, plus dev Google login and explicit account linking.

Source review: November 1, 202610 core + 4 opt-in dev Google routesNo frontend UI implementedSynthetic examples only

Two proofs, two places. The origin token proves an allowed CloudFront path. Password verification establishes the user at login. Later requests prove possession of an opaque cookie whose server records must still be valid.

The supplied plan reports the operator successfully exercised login, chat, follow-up, logout and me returning 401 afterward. That limited operator report is not a new validation run for this guide, proof of browser behavior, or coverage of every denial/race path.

The existing authorizer has two branches

Secret cache, request budget and authorization cache are different

The warm instance keeps only a validated origin secret for up to 300 seconds. Expired-cache refresh uses GetSecretValueCommand({SecretId, VersionStage: 'AWSCURRENT'}), at most two SDK attempts, bounded connection/request timeouts and a request deadline; stale values are not an outage fallback.

createAuthorizer() configures policy-cache TTL zero and only the origin-header identity source, not a global Cookie identity source. Chat's ten-second authorizer uses one createAuthRequestBudget budget (at most remaining runtime minus two seconds) across secret and session/user reads. Session/user authorization is never cached. Ordinary auth routes keep their existing origin-only admission behavior.

Factories and the auth budget

createBffAuth() constructs Cognito/session/user helpers and returns methods that retain config, clients, clock and budget through closures. Constructing the helpers does not itself authenticate a user. A 25-second Lambda has at most 20 seconds of auth work; individual SDK calls use authRequestOptions, capped by that same deadline with response reserve. The HTTP parser supports bounded canonical base64 auth bodies; the chat parser separately rejects base64 bodies.

Separate first-login branch: create metadata only when genuinely absent

readForProvisioning uses a strongly consistent read with malformed-existing-record rejection. Only a genuinely absent eligible account item reaches initialize(sub): a PutCommand for the same five-field USER shape, version 1 and disabled false, conditioned on attribute_not_exists(PK). No existing version/disabled value is reset. A confirmed conditional-initialization loser continues only to the bounded strong snapshot read; other errors propagate.

This metadata creation can happen before a password is accepted. It is provisioning, not proof of authentication or session issuance; a denied password can leave metadata but no session. Missing USER data during cookie resolution is never initialized. Deleted revocation metadata must not be treated as an account-recovery mechanism; operator recovery remains separate.

06 / Commit the session against the original state

One conditional transaction → one stored session

Source — already-created session helper: sessions.create() → requireTrustedAuthenticationContext() → currentAuthTime() → randomBytes(32).toString('base64url') [after subject/token-expiry checks] → sessionKey() → session-record validation → randomUUID() [stable transaction request token] → authRequestOptions() → client.send(TransactWriteCommand) → return the created session.
Setup and conditions: createAuthSessionStore() ran earlier in stage 4. Failed subject/expiry/record checks skip the transaction; failed transaction conditions skip the successful return. SDK retries reuse the prepared command/record/token, not a second call to sessions.create(). Hashing inside sessionKey() is createHash('sha256').update(token, 'utf8').digest('hex').

Attribute/controlMeaning here
__Host-, no Domain, Path=/Supporting browsers require Secure, root Path and host-only scope for this prefix. Path is a delivery scope, not an application authorization boundary.

Work budget before and after password dispatch

The 25-second Lambda's createAuthRequestBudget() allows at most twenty seconds of work with response reserve. mutate() refuses dispatch if the budget is aborted or below 10,000 ms remaining; its call is capped at 4,000 ms. Manual reconciliation, not automatic retry

Follow the existing administrator reconciliation guide: independently identify the exact canonical association and owner/guard records, compare the recorded hashes, preserve USER identity/disablement, and conditionally finish missing revocation/bookkeeping only when justified. Release only resolved owner-matched guards. COMPLETED plus LINKED means cleanup, not another increment. If unresolved, retain the fence/reservation. No negative lookup, larger USER version or cookie clearance alone proves this attempt committed or did not commit.

A missing owner is not comprehensive historical-link evidence; manual/out-of-band changes require reconciliation before using this flow. Do not reset missing USER metadata to version one, free a reservation from an empty association read, or repeat an uncertain link to force progress. There are no new recovery commands, public admin APIs or automatic repair workers here.

MVP limits remain. One linked Google identity; no unlink/replacement/merging or Google-first password enrollment. Cross-service, concurrent account/session and browser-response races remain accepted boundaries.
