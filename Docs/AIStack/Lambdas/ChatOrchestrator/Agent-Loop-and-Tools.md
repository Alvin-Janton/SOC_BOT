# Agent Loop and Tools

This guide follows the investigation inside one accepted turn. See [request/streaming](Request-and-Streaming.md) for the outer handler, [RAG integration](RAG-Tools.md) for document calls, and [persistence/context](Persistence-and-Context.md) for saved state and recovery. The [Code Guide](Code-Guide.md) maps the runtime modules.

## One model cycle

[Orchestrator.run()](../../../../infra/lambdas/ai/chat-orchestrator/orchestrator.ts) starts by counting this logical turn's existing `TOOL_CALL` events and calling `ToolExecutor.recover()`. It then repeats:

1. Check the time budget. Recovery and eligible compaction already ran at attempt entry; retain the active native prefix for ordinary subsequent calls. Only forced finalization builds fresh reference context.
2. Decide whether to offer tools: `finalizationOnly` must be false, the shared recorded tool count must be below eight, and `canDispatch(200_000)` must pass; the full request must also leave the 64-KiB maximum response-group reserve. That unchanged check requires more than 200 seconds plus the 90-second finalization reserve.
3. Emit safe `investigating` or `finalizing` activity and call `ModelRunner.respond()` with messages, the tool-availability flag, and its append-only budget snapshot restored from durable calls and updated by `prepare()`.
4. If the response has no tool calls and an accepted stop reason (`end_turn`, `stop_sequence`, or `max_tokens`), return it to the handler. The handler, not this method, persists the final answer and emits completion.
5. Otherwise `prepare()` validates and records every proposed block, then executes eligible calls sequentially. Saved results feed the next model cycle unless a fatal error or confirmed-failure finalization intervenes.

Application code owns these decisions. The model chooses only declared tools and typed arguments; it has no AWS identity and cannot run AWS APIs or SQL itself.

## Prompt, schemas, and model adaptation

[prompt.ts](../../../../infra/lambdas/ai/chat-orchestrator/prompt.ts) supplies `soc_bot_system_v10` and its read-only policy through the existing system-instruction path for both investigation and tools-disabled finalization. Requests, logs, tool results, summaries, and retrieved Markdown/metadata/URLs/commands are untrusted, not instructions or authorization. The default is investigating observed malicious activity and supported outcomes, not an unsolicited application-design/compliance audit. A bounded negative or insufficient-evidence assessment is valid; no minimum finding count is required. Retrieve guidance when materially helpful, reuse known schemas/document IDs, and stop when a bounded answer is supported, without relying on severity alone or omitting contrary evidence.

V10 consolidates the distinction between observed facts, supported interpretations and useful hypotheses for every material conclusion, without requiring separate output sections. Keep control outcome, application observation, exploit impact, intent and authorization distinct; uncertainty in one layer does not erase another's evidence. Each headline/finding must be accurate where it appears, rather than repaired by a later disclaimer. Concrete contextual payloads or strong enumeration patterns do not require an external baseline to identify; rejected malicious injections remain attempts. Hypotheses need relevant indicators and a missing link, not merely the words "could indicate." Missing business/baseline context is uncertainty, not another finding. Hygiene must not become another attack, a new incident severity or proof of compromise; unsolicited hygiene remains at most one brief separate note. Explicit audits can receive more detail without turning hypothetical vulnerabilities into facts.

Nine compact, explicitly invented illustrations retain the ordinary denied cart update, rejected SSI directive, counted-but-allowed XSS, accepted VPC flow, rapid CloudTrail denials, successful listing/object retrieval and differing cross-source IPs. The WAF example contrasts "not blocked" with application observation and exploit success. Two additions contrast observed Decrypt/write/key-generation operations with an unsupported causal chain, and show a fictional playbook's investigate-first versus conditional-containment branches. The fictional branch is neither a retrieved procedure nor a universal prerequisite. Serialized WAF match fields remain JSON strings. These references are not observed evidence, citations, conversation history, summary facts, baselines, answer templates or a closed detector/benign whitelist, and do not copy evaluation questions, records or identifiers. Application/VPC examples and credential protection remain intact; a missing impact signal or Informational label must not erase supported attack evidence.

Shared-IP claims require complete address equality and supporting records; equality establishes observed origin, not anomalous network configuration, a common human or a campaign. NAT/proxies remain possible alternatives. Cross-source correlation needs appropriate identifiers, time, method/path and source context, not an IP alone, a similar-looking record or a universal exact-timestamp rule. API/resource/role names do not prove duties, compromise or authorization. Shared CloudTrail identity/time establishes a sequence, not common content or causation: decrypt-write-key-generation narratives need resource/content/context links. Successful listings/object reads remain observed access when authorization/sensitivity is unknown, without inflation into theft or dismissal as harmless. An absent listing prefix does not prove all bucket objects were enumerated; DescribeSecret is metadata access, and denied reads do not establish exposure. No baseline retrieval or deterministic correlation layer is added.

Before answering, the prompt asks the model to verify exact material IPs/identifiers, counts/components, time bounds, outcome wording, links and recommendation prerequisites against retrieved results. Correct/remove unsupported clauses where they appear, without invented details, private reasoning or a visible checklist. These are behavioral instructions, not guaranteed semantic, correlation or completeness enforcement. Model construction, pinned signed context, summaries, tools, validation, budgets, replay, diagnostics and runtime finalization remain unchanged; adherence requires operator review after deployment.

For user-facing answers, lead with the assessment and investigated UTC scope, include material findings and representative evidence, then important limitations/proportionate next steps when warranted. Soft targets remain 100-200 words for benign/routine investigations and 250-400 for multi-finding incidents, unless more detail is requested. Combine minor uncertainties; omit ordinary-user timelines, hypothetical chains, redundant control tables and blanket hygiene audits unless requested or materially supported. Brevity must preserve attack categories, exceptional outcomes, contrary evidence, corroboration gaps, prerequisites and safety warnings. Copy complete evidence identifiers; a shared source key can be cited once for a clearly identified group. Answer-format/length instructions do not apply to generated summaries; `SUMMARY_INSTRUCTION` and compaction mechanics are unchanged.

Exact counts require complete aggregates or verified deduplicated evidence, not overlapping totals, truncated groups or conflating grouped combinations with distinct entities. Sampled payload inspection is not full coverage, and negative conclusions must stay within queried evidence. HTTP 200 does not establish business/authentication/exploit success; HTTP 403 does not identify WAF as the cause or prove nothing executed. WAF ALLOW, network ACCEPT, client-supplied prices and successful API access do not independently prove malicious intent, payload execution, missing validation, unauthorized access or exfiltration. Stronger claims require source-specific corroboration.

The prompt prohibits reproducing passwords/passphrases, keys/secrets/tokens, authorization headers, session cookies/IDs, private keys, full payment-card values and unnecessary personal identifiers, including synthetic values and values inside encoded URLs, bodies, tables, quotations or follow-up summaries. Name the affected field and cite evidence instead; use `[REDACTED]` only when a structural example is necessary. Keep justified credential/PII logging observations brief and separate from attack findings, without inferring transport, compliance or exploitation from field presence. This is model guidance, not deterministic redaction or semantic validation; neither the answer nor the unchanged temporary dev preview is guaranteed free of sensitive values.

Only log queries require time ranges. The [compiler](../../../../infra/lib/stacks/ai/query-contract.ts) uses an inclusive start and exclusive end: a full UTC day is `00:00:00Z` through the next day's `00:00:00Z`, not `23:59:59Z`. Preserve requested subwindows. No compiler acceptance/SQL, evaluation-case or tool input schema changes accompany these instructions.

### Source fields and per-query completeness

The existing `tableFacts()` JSON reference in [contracts.ts](../../../../infra/lambdas/ai/chat-orchestrator/contracts.ts) keeps all four `tables` column lists and `utc_query_window_days`, with `source_semantics`, `filter_semantics`, `operation_semantics`, `evidence_semantics` and `query_result_semantics`. The model adapter sends it through the same labeled reference system block; no additional service, retrieval step or model request is introduced. These are authored contract descriptions, not tool permissions or instructions obtained from log values. Tool input schemas/descriptions, SQL/acceptance and successful result objects are unchanged; local-rejection hints are described below.

Application method/path/URL/query/body/header fields describe the incoming request, not returned HTML; non-null parameter maps and headers are JSON-serialized strings. A request `errorMsg` value does not establish authentication failure, reflection, redirect or response contents. Actual response bodies are absent. `status_code` is the recorded HTTP code; `status` is merely success below 400 and failure otherwise. Response bytes/latency are metadata, not disclosed-content evidence. `actor` comes from `session_id`, not a verified user or unique human, and its value must not be echoed. Provenance combines object key, source-specific record reference and relevant time; deterministic IDs need not identify unique occurrences. These verified application mappings are not asserted for the other tables.

For successful terminal data queries, `result_count` counts returned rows, not table size/all matching events. Aggregates return metric/group rows: path/method groups are not distinct paths, and a `count_rows` value is not the number of returned groups. `truncated=true` means matching result rows were omitted for `row_limit` or `response_size`. `truncated=false` means complete for that query's filters/range/projection, not a complete-table/payload inspection or an attack outcome. These rules do not turn submitted/running/error results or metadata descriptions into completed evidence.

Completeness stays local: a truncated IP breakdown does not invalidate a separate complete count or complete filtered result, while complete aggregates do not establish payload coverage. If omitted rows could change the assessment, use existing aggregates, narrower filters/windows, fewer fields or a higher permitted limit suited to the cause; requesting more rows alone does not fix `response_size`. Stay within budgets and disclose unresolved gaps rather than automatically fetching everything or inventing pagination, HAVING or distinct-count operations. No backend behavior/cap changes implement these instructions.

### CloudTrail identity and NULL-aware coverage

`identity_user_name` preserves only native `userIdentity.userName`; it can be NULL for role sessions, services, federation or incomplete records. `actor` uses native ARN, then username, otherwise NULL, not a new principal-ID mapping or universal human identifier. Use identity type, actor, source IP, resource and full event provenance together. No new normalized column or imputed username is introduced.

Filters remain AND-only and retain ordinary SQL NULL behavior: `ne` emits `<>`, and inequality, equality, IN and ordered comparisons do not match NULL. `is_null`/`is_not_null` must omit `value` entirely. Excluding named users therefore does not retrieve every other principal; a separate bounded missing-value query or supported identity/event dimension may be appropriate. `describe_table` exposes selectable columns, not every grouping/comparison. `operation_semantics.aggregate_group_by` is copied from the compiler's existing grouping map, not a second allowlist; ordered comparisons require numeric/timestamp fields, while numeric metrics require int/bigint fields.

The retained policy covers successful and failed activity across identity types and reconciliation of narrower timelines with available complete aggregates. Material missing populations should receive targeted follow-up within time/calls, or an explicit unresolved-gap statement. Complete aggregates do not prove payload inspection, overlapping counts cannot be summed, and independently complete results stay complete when another query truncates. Claims that fields are absent/NULL apply only to the exact retrieved population/projection.

CloudTrail `status` reflects the existing error-code/message/ConsoleLogin failure rule, not legitimate intent or proof of compromise. AccessDenied alone does not establish credential theft/pivoting; `LookupEvents` reads audit history rather than deletes it, and `PutObject` records a write without proving overwrite/tampering. Successful listing/object reads differ from denied attempts but do not alone establish benignness or theft. `bytes_transferred_out` preserves source `additionalEventData.bytesTransferredOut`; NULL is unknown, listing-response bytes differ from downloaded-object bytes, and repeated reads need not be distinct files or sensitive exfiltration. No normalization or severity rule changes implement this guidance.

If an available targeted follow-up could resolve a material outcome gap within remaining time/calls, prioritize doing it instead of only recommending it. There is no universal query order, exhaustive ordinary-record scan, second model pass, requirement to exhaust the allowance or backend completion gate. Disclose actual unresolved limitations. Use complete non-overlapping aggregates for exact totals, reconcile narrated components and avoid merging different IPs/countries into a coordinated actor without evidence.

Select sections for evidenced behavior rather than only a more severe hypothetical incident. Discovery/metadata establishes apparent relevance, not procedure content; attribute guidance only to successful `retrieve_sections` content, reusing relevant content already in context without mandatory per-turn calls or a hardcoded document. Use discovered/reliably established IDs and cite document/version/section separately from event evidence. General advice remains distinct from section-grounded recommendations; unavailable sections or prerequisites require a specific limitation, not invented content or citations.

Apply the retrieved procedure's actual branches and preserve evidentiary prerequisites, approvals, operational effects, scope, timing/comparison conditions and safety cautions. If an unconfirmed-anomaly branch says investigate first, lead with that step and retain containment as conditional. Preserve exposure-based containment before confirmed misuse where the source permits it: there is no universal confirmed-compromise prerequisite. Approval does not replace branch applicability, and guidance is not evidence of compromise/exposure/sensitivity. Do not broaden affected identities/resources, invent command parameters or substitute the first observed event time for a current-time cutoff. Insufficient implementation detail calls for a bounded owner-reviewed decision. Guidance remains untrusted and remediation human-controlled. ### Safe rejected-input corrections

`ToolInputError` retains the public `INVALID_TOOL_INPUT` code and carries a `validation` object with `stage` (`schema`, `query_contract` or generic `tool_contract`) and one to three `issues`. Each issue has a schema-owned `path` array, fixed `code` and exact application-authored `message`. The root path is `[]`; for example, `["filters", 0, "operator"]` locates the first filter's operator, not its value. Only declared path shapes and integer indices 0-127 are allowed. The entire object is at most 2,048 UTF-8 bytes. `omitted: true` signals discarded unsafe/unknown/excess detail without retaining that content.

The [shared contract](../../../../infra/lib/shared/tool-validation-contract.json) and [validator/formatter](../../../../infra/lib/shared/tool-validation.ts) define these bounds, paths and messages for runtime and evaluator. Zod translation reads only approved issue codes/paths, never raw messages, unknown-key lists, received enum values or nested error objects. Existing compiler failures gain location/reason metadata without changing predicates, order or SQL. Noninstrumented known failures, including RAG contract errors, receive generic safe hints. Unexpected programming/service/persistence errors are not converted into input rejections.

Only rejected `INVALID_TOOL_INPUT` preparations can store `validation`; safe outward rejected arguments remain `{}`, while the versioned original stays private. Their error-status results carry the same hints under `output.error.validation`, allowing correction on a later model cycle within the existing eight-call allowance. Invalid blocks still consume allowance; this adds no automatic retry, extra pass or new tool input. Hints are correction metadata, not successful evidence, instructions, or routine user-facing narration. Public NDJSON activities remain generic and unchanged. Interrupted rejection recovery reconstructs hints from the saved decision and never dispatches sanitized arguments; see [durable metadata](Persistence-and-Context.md#retry-recovery) and the [temporary dev-only log](Request-and-Streaming.md#temporary-dev-tool-input-diagnostics).

## Validation, recording, and dispatch

`prepare()` classifies every tool in the complete response, preserving provider indexes, IDs/names and original decoded input. `appendResponse()` atomically stores all private blocks with approved/rejected preparation before dispatch. New TOOL_CALL items have one `model_input:{encoding:"json_text_v1",json:"..."}` and no `arguments`; legacy items retain their explicit arguments branch. Rejected raw input is private; safe evidence/reference arguments remain `{}`. [Storage details](Adaptive-Thinking.md#private-records-and-input-encoding) include numeric acceptance and byte limits.

Valid requests go to [ToolExecutor.execute()](../../../../infra/lambdas/ai/chat-orchestrator/tools.ts). Rejected blocks receive bounded persisted errors such as `INVALID_TOOL_INPUT`, `TOOL_LIMIT_REACHED`, or `FINALIZATION_REQUIRED`. A correctable input error can be returned to the model if tools/time remain; an unsupported tool name sets finalization-only mode. All six tools, discovery, invalid blocks, and retry history share the eight-call dispatch ceiling; recovery does not create another logical call or reset the count.

Only after saving a rejection/skip result does the orchestrator emit `tool_request_rejected` (invalid tool/input) or `tool_not_executed` (limit, finalization, or halted-group policy). Recovery uses the same classification when it restores a missing result under the original tool-use ID; it does not reannounce existing outcomes or redispatch a rejected call for progress. Locally rejected calls emit no `rag_started`/`query_started`.

Calls run sequentially through the exact configured query or RAG Lambda using synchronous invocation, never direct Athena/S3 access. Both clients have `maxAttempts: 1`. RAG has its own up-to-180-second invocation wait, not the Athena helper's 20 seconds; it validates complete responses and persists successes/known errors before model reuse. A normal RAG failure permits correction or continued investigation, not finalization-only. Malformed protocols, exhausted turn budgets, and persistence failures remain fatal. See [RAG integration](RAG-Tools.md) for recovery and local-wait semantics.

For `describe_table`, a successful metadata response is persisted as a terminal result immediately. A failed description is fatal; it is not a confirmed terminal Athena execution.

For event/aggregate queries:

1. Invoke the query Lambda and require a valid execution ID with `SUBMITTED`.
2. Save a `TOOL_RESULT` checkpoint containing the ID, original validated query, and `submitted_at_ms`. It is not final evidence despite its storage `status: success`.
3. `poll()` calls internal `query_status` with that exact request/ID. It checks identity, operation/table, and recognized states. Between calls it waits up to one second without exceeding the original query deadline.
4. On verified success, persist the bounded rows before emitting `query_completed`. On verified `FAILED`/`CANCELLED`, persist a bounded failure before returning control to the orchestrator.

Unknown dispatches, missing execution IDs, unavailable state, malformed responses, or persistence failures are fatal. The system does not invent success or resubmit a query whose submission is uncertain.

Failure activities distinguish a validated backend application error (`tool_error`), an invocation/transport/function-error/local-wait failure (`tool_invocation_failed`), and an undecodable or invalid response (`tool_response_invalid`). Confirmed Athena failures emit `tool_error` only after their bounded terminal result is persisted; existing fatal backend errors, such as a failed table description, remain fatal and do not imply a saved result. Internal status/cancellation calls retain the original logical tool-use ID, do not increase the tool count, and emit at most one failure activity per call per attempt rather than one per poll. Narrow invocation/response boundaries emit safe activity before propagating the original fatal failure; storage or stream failures are not relabeled as invocation failures. Activities are informational, not durable audit records or proof that uncertain backend execution stopped. See [streaming outcomes](Request-and-Streaming.md#tool-activity-outcomes).

## Query deadlines and cancellation

The query deadline is 180 seconds or 3 minutes from the saved submission time, including submission/polling overhead. It is enforced here, not by a blocking timer inside the query Lambda. `timedOut()` invokes internal `cancel_query`; `cancelActive()` checks the returned ID/state and records what was observed.

A successful stop request is not proof of `CANCELLED`: the query Lambda normally returns the pre-stop state with `cancellation_requested: true`. The current orchestrator does not wait in a separate cancellation-confirmation loop. A still-queued/running response remains a pending checkpoint, and `timedOut()` raises `QUERY_TIMED_OUT` unless a terminal failure was independently observed and saved. The handler makes a best-effort cleanup call on its fatal path; it does not claim an unconfirmed stop succeeded.

If a terminal `FAILED` or `CANCELLED` state is observed and durably saved, it can use the handled-failure path below. A late success is not accepted merely because cancellation raced with completion. Poll/recovery accepts a success observed after expiry only when authenticated service completion time proves it finished within the original deadline; expired recovery otherwise follows cleanup.

Cancellation is internal only. There is no model-selectable cancellation tool, browser Stop endpoint, or active authenticated ownership integration. Workgroup validation in the query Lambda does not establish user ownership. A client disconnect is not cancellation.

## Confirmed failure and finalization

`isConfirmedQueryFailure()` recognizes the saved bounded result of a verified execution with `FAILED`/`QUERY_FAILED` or `CANCELLED`/`QUERY_CANCELLED`. After one such result, `run()`:

1. Sets `finalizationOnly`.
2. Persists `NOT_EXECUTED` results for later queued calls in that model response.
3. Rebuilds context and asks the model for an explanation with tools disabled, using previously collected evidence and the limitation.

This ends tool use for the entire logical turn, not just that batch. It also applies to confirmed timeout cancellations; there is no automatic narrower-query retry in this MVP. A new user turn can investigate again. Retrying the same logical turn reuses the saved failure and still finalizes with tools disabled.

Final explanation becomes a completed assistant event only if model synthesis and persistence succeed. Unknown submissions, unconfirmed cancellation, and storage/fencing/model errors remain fatal turn-outcome errors. A failed write of the failure result or later `NOT_EXECUTED` results is not treated as handled success.

## Bounds and recovery
