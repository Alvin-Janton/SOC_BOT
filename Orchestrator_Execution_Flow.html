Private dev chat Lambda / query_events example

From a chat message
to an evidence-backed answer.

Follow the data through the handler, conversation store, Bedrock tool loop, private query Lambda, Athena, and the final streamed response.

Code snapshot: October 10, 2026 Orchestrator implemented in dev source API & Cognito integration deferred

Two different functions: the chat orchestrator manages the conversation and model loop. The query-tool Lambda executes the approved Athena operations. Bedrock proposes a tool call; application code decides whether to execute it.

All example IDs, rows, times, answers, and counts are illustrative, not captured production output. Reduced examples show selected fields and are labeled. This document explains current source behavior; it neither deploys nor invokes anything.

Companion: Query Execution Flow covers the query internals in more detail. That earlier document is an October 7 snapshot; its statements that orchestration and Lake Formation are deferred are historical, not the current implementation status.

One turn / several service calls

The end-to-end route

  1. Chat input → trusted requesthandler → respond → configuration + parseRequest
  2. Trusted request → durable conversationConversationStore.begin checks ownership, takes a lease, and saves one user event.
  3. History → bounded model contextToolExecutor.recover + Orchestrator.context + buildContext
  4. Bedrock context → proposed tool blockModelRunner.respond → request → ConverseStream
  5. Tool block → validated, saved callOrchestrator.prepare → validateTool → store.append
  6. Typed request → running Athena queryToolExecutor.execute → invoke → query handler → start → compileQuery
  7. Execution ID → bounded evidencepoll → query_status → execution + boundedResults → terminal
  8. Saved evidence → model answerThe loop rebuilds context and calls Bedrock again; only approved calls may repeat within the cap.
  9. Answer → durable completiontext_delta → ASSISTANT_MESSAGE → release → complete

Where the security data comes from

Prepared raw logs in S3
  -> separate on-demand Glue ETL run
  -> source-specific normalized Parquet + Glue Catalog tables
  -> Lake Formation table grants / normalized-prefix governance
  -> Athena reads the approved table when the query tool requests it

This preparation is NOT performed inside a chat invocation.

The example uses waf_events, but the same conversation loop can request application_events, vpc_flow_events, or cloudtrail_events. Schemas remain source-specific.

02 / store.ts + handler.ts

begin() establishes the durable turn

respond() creates the normal conversation store and a cleanup store with the same table/owner but different operation deadlines. It then calls:

store.begin(
  request.conversationId,
  request.turnId,
  request.message,
  leaseExpiresAtSeconds,
)
  1. If this is a new conversation, initialConversationId() derives a stable UUID from the table, trusted owner, and first turn ID; createConversation() writes its metadata conditionally.
  2. metadata() checks the stored owner using a strongly consistent read. events() loads bounded event history and orders it by numeric event_sequence.
  3. checkTurn() checks idempotency: same ID with different message is a conflict; completed work replays; nonretryable outcomes cannot be restarted.
  4. A conditional metadata update acquires the attempt-owned lease and increments its fencing version. A still-active lease prevents a competing invocation.
  5. The original USER_MESSAGE is appended only if absent. Expired prior attempts can receive a lease-recovery outcome.
Acquired result · selected fields, example IDs 
{
  "state": "acquired",
  "lease": {
    "conversationId": "c4e7173b-3075-47b9-9e7d-260921bbc870",
    "turnId": "296a0470-b7b7-4a21-a9d7-72fb7be90ac9",
    "attemptId": "b7777777-7777-4777-8777-777777777777",
    "version": 1,

The real acquired result also contains events and userEvent. The example conversation UUID illustrates a format; it is not a computed hash result for the sample request.

Conversation identity

conversationId groups history. turnId identifies one logical user submission. attemptId identifies a particular execution/retry.

Write ordering and ownership

append() → appendFor() condition-checks owner, active attempt, fence, expiry, and sequence in the event-write transaction. This prevents a stale writer from appending to a newer attempt.

Conversation metadata: PK = CONV#<conversationId>   SK = META
Event:                 PK = CONV#<conversationId>
                       SK = EVT#<UTC-created_at>#<10-digit-sequence>#<eventId>

Numeric event_sequence is causal order, even if clock timestamps regress.

After acquisition, respond() opens the NDJSON response and emits the conversation and turn IDs. Completed turns take the shorter replay branch described below.

03 / orchestrator.ts + tools.ts + context.ts

History becomes model context, not a database dump

Orchestrator.run(initialEvents) counts all previously stored tool blocks for this turn, then calls tools.recover(initialEvents). A new turn has no prior calls, so recovery does nothing. A retry follows the saved-state recovery rules.

Orchestrator.context() reloads fenced history and any saved summary. buildContext() reconstructs user messages, original assistant tool groups, exactly one selected terminal result per call, and completed assistant answers.

Initial messages array · first conversation, no tools yet 
[
  {
    "role": "user",
    "content": [
      {
        "text": "Show up to two WAF events on September 11, 2026 UTC with severity 3 or higher. Include action, path, and severity ID."
      }
    ]
  }
]

This is a Message[], not DynamoDB item JSON. Internal owner IDs, lease fields, turn outcomes, and event-storage keys are not copied into this conversational history. Tool arguments and bounded results are included as investigation data.

What happens when history grows?

Context construction permits at most 192 KiB and 128 messages. Around 96 KiB, planCompaction() finds eligible older complete prefixes; ModelRunner.summarize() summarizes up to twelve completed turns at a time while retaining six recent completed turns.

saveSummary() persists the bounded summary and covered-through event pointer. Full audit events remain stored. Unresolved retryable/active turns block compaction; abandoned turns and failed prose/outcomes are excluded. Context and compaction reuse the same original call/result selection.

Historical completed tool evidence is bounded by that turn's saved assistant-message sequence, so later audit records cannot silently rewrite the evidence behind a past answer.

04 / model.ts + contracts.ts + prompt.ts

Bedrock proposes a tool; it does not execute one

run() computes whether tools are allowed, emits investigating or finalizing activity, and calls ModelRunner.respond(messages, allowTools, budget, emitText). Its private request() calls Bedrock ConverseStream.

  • The stable versioned system prompt declares the read-only role and treats log values, catalog text, and summaries as untrusted data.
  • tableFacts() supplies column/type facts and the query-window cap separately from the stable prompt.
  • bedrockTools() derives schemas from the strict Zod definitions for describe_table, query_events, and aggregate_events.
  • The stream parser collects text and tool blocks, validates block order/IDs/stop reasons, parses each tool's JSON input, and excludes private reasoning.

05 / Orchestrator.prepare + validateTool + store.append

The proposed call becomes an approved request

prepare(response) processes every tool-use block before dispatching any of them. Each block counts toward the four-call logical-turn cap, including invalid or excess blocks.

  1. Assign one assistant_message_id to preserve the original response's tool group and each block's index.
  2. Check the call count and whether dispatch plus finalization fits the remaining budget.
  3. validateTool(name, input, config) checks the strict tool schema and creates { operation: name, ...parsedInput }.
  4. For data queries, compileQuery() independently rechecks business allowlists, typed filters, times, projections, and limits. This validation pass does not execute SQL.
  5. Append a TOOL_CALL. Validated arguments are structured DynamoDB attributes, not a flattened string. Invalid input is not copied into audit history.

06 / tools.ts → query-tool/handler.ts

Start the query, then save its execution ID

ToolExecutor.execute() emits safe query_started activity. invoke() serializes the validated request into the Lambda SDK payload and invokes only the configured private query function. It parses the returned payload back into a bounded JSON object.

Inside the query Lambda, handler() dispatches to start(). compileQuery() generates controlled SQL with approved columns, daily partition predicates, exact UTC time bounds, typed escaped filters, deterministic sorting, and LIMIT 3 for our two-row request. The extra row detects truncation; it is not an extra row promised to the caller.

StartQueryExecution submits this SQL to the environment's dedicated workgroup. Athena continues after that query-tool invocation returns.

If the start invocation is ambiguous and no execution ID is durably known, the orchestrator fails closed. It does not blindly submit the query again.

07 / ToolExecutor.poll + status + query-tool results

Polling uses the original request, not just an ID

poll() repeatedly invokes internal query_status within the original 180-second query budget. Calls are followed by bounded waits of up to one second while the query remains pending.

Internal status invocation 
{
  "operation": "query_status",
  "query_execution_id": "11111111-1111-4111-8111-111111111111",
  "query": {
    "operation": "query_events",
    "table": "waf_events",
    "start_time": "2026-09-11T00:00:00Z",
    "end_time": "2026-09-12T00:00:00Z",
    "fields": ["action", "path", "severity_id"],
    "filters": [{"field": "severity_id", "operator": "gte", "value": 3}],
    "limit": 2
  }
}
  1. Query status() recompiles the supplied original request.
  2. execution() retrieves the execution and verifies the exact environment workgroup.
  3. The query Lambda compares recorded SQL, database, and catalog against the approved compiled request. A mismatched request cannot fetch evidence.
  4. QUEUED/RUNNING returns metadata only. SUCCEEDED permits one bounded GetQueryResults page.
  5. boundedResults() verifies the header/row width and calls cell() to convert Athena strings into named, typed fields.
  6. The orchestrator checks the returned execution ID, operation, table, state, and failure contract before treating a status as confirmed.
How Athena cells become evidence fields
Athena value / declared typeReturned value
"3" / intNumber 3, such as severity ID.
"9007199254740993" / bigintString, preserving precision beyond safe JavaScript integers.
Missing cellnull, not an empty string or zero.
TimestampUTC timestamp text, such as 2026-09-11T09:00:00.000Z.

The query compiler automatically includes event_uid, event_time, source_type, source_s3_key, and source_record_ref, even when only a few display fields were requested.

selectToolResult() chooses existing terminal evidence ahead of pending checkpoints; original tool groups and call order remain intact. No result is copied into a new attempt just to make it visible.

Success does not automatically disable tools. If call/time budgets permit, Bedrock can request another approved tool or answer immediately. For a no-tools request, modelMessages() projects prior tool calls/results into labeled untrusted JSON text and omits tool definitions. This provider-input conversion leaves the original stored audit events unchanged.

09 / ModelRunner + respond + NdjsonStream

The answer streams, then completion becomes durable

Assume the next model response answers rather than requesting another tool. ModelRunner returns a response with empty toolUses and an accepted stop reason. run() returns that response to respond().

During tools-disabled synthesis, public text deltas stream as they arrive. During a tool-capable request, text is buffered until the stop reason confirms it is an answer rather than another tool request. Tool-capable final text is then emitted in chunks.

NdjsonStream.emit() serializes and queues safe events. While idle it may emit generic 15-second heartbeats. finish() attempts at most one terminal event and closes the response. Additional activity/chunks may occur; the lines above are a selected sequence, not an exact event-count contract.

Handled query failure / not fabricated evidence

A confirmed query failure still permits an explanation

If the checked query reaches FAILED or CANCELLED, failed() saves a bounded error result. It does not expose provider diagnostics or invent rows.

Durably saved failure output · FAILED example 
{
  "ok": false,
  "query_execution_id": "11111111-1111-4111-8111-111111111111",
  "state": "FAILED",
  "halted_tool_group": true,
  "error": {
    "code": "QUERY_FAILED",

Verified final state
  -> await bounded error TOOL_RESULT persistence
  -> return failure output to Orchestrator.run()

  -> rebuild context with earlier evidence + this failure
  -> ConverseStream with NO tool definitions

For example, if one model response queued three calls and the first query failed, calls two and three are not invoked. Their original TOOL_CALL records remain, each paired with a bounded NOT_EXECUTED result.

isConfirmedQueryFailure() recognizes the verified failure contract after persistence. Saving the failure or any queued rejection must succeed before the final model request can happen. A storage failure remains fatal.

At a query deadline, timedOut() → cancelActive() attempts internal cancellation. If an actual FAILED/CANCELLED state is observed and saved, the same result is reused; no second synthetic timeout result is appended. A requested but unconfirmed stop remains fatal.

A completed explanation is not a successful query. The model must say that evidence was unavailable and use only earlier verified evidence. If final synthesis or final answer persistence fails, the turn follows the fatal-outcome path.

What the fatal handler path does

respond() catches fatal failures and publicError() maps them to safe codes/messages. It attempts cleanup for a tracked active query and writes a bounded TURN_OUTCOME when persistence permits. No placeholder is saved as a completed assistant answer.

Before streaming starts, httpError() sends an ordinary HTTP JSON error. After streaming starts, the handler attempts one NDJSON error event. Raw SDK error text, stack traces, SQL, arguments, and evidence rows are not streamed or logged.

An ambiguous final assistant write might already have committed. The handler does not append a contradictory failed outcome: it reports OUTCOME_NOT_CONFIRMED and keeps the lease for expiry recovery. Failure to confirm any other outcome is also reported honestly.

Internal cancel_query is not exposed to Bedrock or as a browser endpoint. A future authenticated Stop path must resolve server-side user/turn ownership before invoking cancellation. A disconnect alone is never treated as Stop.

Orchestrator identity

Exact chat-table item access, invocation of the configured query function, and approved Bedrock resources. No direct Athena, Glue, Lake Formation, or security-log S3 permissions.

Query identity

Dedicated workgroup, approved catalog/table metadata, Lake Formation access, and Athena results. No direct raw/normalized/quarantine/evaluation S3 reads; registered normalized data is governed through Lake Formation.

The model has no AWS identity. Runtime roles cannot access hidden evaluation data. Tool output is evidence, not instructions, and severity alone is not proof of maliciousness or exploitation.

CloudWatch logs contain operational identifiers, phases, outcomes, timings, counts, and token totals only. Conversation bodies, tool arguments/results, summaries, credentials, and private reasoning stay out of logs.
