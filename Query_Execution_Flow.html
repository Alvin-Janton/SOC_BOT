Athena query tool / query_events

Query execution,
from request to evidence.

Follow one typed WAF query through the Lambda, the SQL compiler, Athena execution, and the conversion back into compact evidence rows.

Code snapshot: October 7, 2026 Query tool implemented Orchestrator not yet implemented

The essential distinction: query_events submits a query and returns an execution ID. A separate query_status invocation later checks its state and retrieves results. Athena keeps working after the first Lambda invocation returns.

Examples are illustrative, not recorded AWS results. Event hashes, execution IDs, timings, and byte counts are placeholders. This file documents behavior; opening it does not execute a query.

01 / Invocation A

Input enters handler()

Imagine the caller asks: “Find WAF events on September 11 with severity 3 or higher. Return action, path, and severity ID, with at most two events.”

Lambda event · originalQuery 
{
  "operation": "query_events",
  "table": "waf_events",
  "start_time": "2026-09-11T00:00:00Z",
  "end_time": "2026-09-12T00:00:00Z",
  "fields": ["action", "path", "severity_id"],
  "filters": [
    { "field": "severity_id", "operator": "gte", "value": 3 }

This is the direct Lambda payload, not an API Gateway HTTP envelope. context.awsRequestId comes from Lambda's invocation context, separately from the event.

02 / Request becomes a compiled contract

start() calls compileQuery()

const query = compileQuery(
  request,
  config.database,
  config.maxDays,
);

compileQuery() constructs SQL and expected output types. It does not contact Athena or execute anything.

compileQuery(request, database, maxDays)
  |
  +-- object() / onlyKeys()       Validate shape and allowed options
  +-- tableName()                Resolve an approved table
  +-- limit validation           Enforce 1-100 rows; default 25
  +-- queryWindowDays()
  |     +-- timeSql()
  |           +-- utcTime()      Validate UTC timestamps and range
  |           +-- literal()
  |                 +-- stringLiteral()
  +-- filtersSql()
  |     +-- object() / onlyKeys() Validate each filter
  |     +-- column()
  |     |     +-- tableColumns()  Resolve approved names and types
  |     +-- literal()             Format a type-checked value
  |           +-- stringLiteral()
  +-- column() / tableColumns()   Resolve output and sort columns
  +-- add provenance / dedupe     Build the final projection
  +-- assemble SELECT            SQL + limit + expected columns

Validate the contract

The compiler rechecks the plain-object shape, enforces its own 16 KiB request limit, accepts only data-query operations, and rejects unsupported keys. For query_events, the allowed keys are:

operation, table, start_time, end_time,
filters, limit, fields, sort

onlyKeys() checks that no unexpected keys exist. It does not require every allowed key to be present. Required values are validated by their consuming functions; optional fields use defaults.

tableName() accepts only application_events, waf_events, vpc_flow_events, and cloudtrail_events. The database must match the configured dev/demo database convention.

timeSql(): partitions plus exact timestamps

utcTime() validates real UTC ISO-8601 values ending in Z, with up to millisecond precision. The range must be positive, within the configured cap, and within the current 2026-2036 catalog projection.

Time conditions for our request 
(
  ("year" = '2026' AND "month" = '09' AND "day" = '11')
)
AND "event_time" >= TIMESTAMP '2026-09-11 00:00:00.000'
AND "event_time" < TIMESTAMP '2026-09-12 00:00:00.000'

Partition predicates

Narrow which date partitions Athena considers scanning. A multi-day query generates an OR across all covered UTC days.

Timestamp predicates

Narrow which events qualify. The start is inclusive and the end is exclusive, so September 12 at midnight is not included.

filtersSql(): typed filters become SQL

Each filter is validated independently. column() consults tableColumns(), which combines the committed source columns with the projected date partition columns.

{ field: 'severity_id', operator: 'gte', value: 3 }
    |
    +-- severity_id is an approved WAF column
    +-- its type is int
    +-- gte is an approved numeric comparison
    +-- literal(3, 'int') validates and formats the integer
    |
    v
"severity_id" >= 3

literal() formats values according to the column type. stringLiteral() quotes strings and doubles apostrophes so they remain values rather than SQL syntax. Filters are AND-only, with at most eight filters and at most ten values per in filter.

Projection, provenance, and sorting

The requested projection permits 1-20 approved fields before adding provenance. The compiler adds the five required provenance columns and removes duplicate names.

Final column order and declared types
ColumnTypeWhy it is present
actionstringRequested
pathstringRequested
severity_idintRequested
event_uidstringRequired normalized evidence identifier
event_timetimestampRequired event time
source_typestringRequired source classification

With no explicit sort, the compiler uses ascending event_time, followed by event_uid, source_s3_key, and source_record_ref as tie-breakers. These fields are not guaranteed unique for repeated records with the same native ID in the same raw object.

Generated SQL · line-wrapped for readability 
SELECT
  "action", "path", "severity_id",
  "event_uid", "event_time", "source_type",
  "source_s3_key", "source_record_ref"
FROM "soc_bot_dev_security"."waf_events"
WHERE (
  ("year" = '2026' AND "month" = '09' AND "day" = '11')
)
  AND "event_time" >= TIMESTAMP '2026-09-11 00:00:00.000'
  AND "event_time" < TIMESTAMP '2026-09-12 00:00:00.000'
  AND "severity_id" >= 3
ORDER BY
  "event_time" ASC NULLS LAST,
  "event_uid" ASC,
  "source_s3_key" ASC,
  "source_record_ref" ASC
LIMIT 3

Why LIMIT 3? The requested response limit is still 2. The third row is look-ahead evidence that more matching rows exist, not a third row returned to the caller.

03 / The first invocation ends

start() submits to Athena

The compiled object returns to start(), which sends StartQueryExecutionCommand through the Athena SDK client.

await athena.send(new StartQueryExecutionCommand({
  QueryString: query.sql,
  QueryExecutionContext: {
    Database: config.database,
    Catalog: 'AwsDataCatalog',
  },
  WorkGroup: config.workgroup,
  ResultConfiguration: {
    OutputLocation: `s3://${config.bucket}/athena-results/`,
    EncryptionConfiguration: { EncryptionOption: 'SSE_S3' },
  },
  ResultReuseConfiguration: {
    ResultReuseByAgeConfiguration: { Enabled: false },
  },
}), { abortSignal: AbortSignal.timeout(10_000) });

Athena runs the SQL against cataloged normalized data. The Lambda does not directly read the underlying raw or normalized Parquet objects. The dedicated workgroup enforces the result location, SSE-S3 encryption, and a 128 MiB bytes-scanned cutoff.

The 10-second abort signal bounds this SDK request; it is not the lifetime of the asynchronous Athena query. Stopping a query requires cancellation.

First Lambda response 
{
  "ok": true,
  "operation": "query_events",
  "table": "waf_events",
  "query_execution_id": "11111111-1111-4111-8111-111111111111",
  "state": "SUBMITTED",
  "query_deadline_seconds": 180,
  "result_count": 0,
  "truncated": false
}

SUBMITTED is the tool's acknowledgement that Athena returned an execution ID, not Athena's current execution state. There are no result rows in this response.

handler() records operational metadata, including the Lambda request ID, operation, execution ID, elapsed invocation time, and outcome. It does not log SQL, filters, or evidence rows. It then returns to the caller while Athena continues.

The same entry checks run in handler(). This time operation dispatch selects status(request, config).

Status validation and function calls
Function or checkWhat happens

Query matching is not user authorization. These checks prove the execution matches the request and configured workgroup. Server-side user/turn ownership tracking and authorization belong to the future orchestrator/API slice.

Submission and completion timestamps describe query execution, not the timestamps of the security events. For QUEUED or RUNNING, no result page is fetched. The caller can invoke status again later.

05 / Athena reports SUCCEEDED

status() fetches one bounded page

const result = await athena.send(new GetQueryResultsCommand({
  QueryExecutionId: id,
  MaxResults: expected.limit + 2,
  QueryResultType: 'DATA_ROWS',
}), { abortSignal: AbortSignal.timeout(10_000) });

For our requested limit of two, the page can contain four rows: a header, two requested evidence rows, and one extra evidence row for truncation detection.

Athena's SDK representation is positional: each cell corresponds to a selected column. Values initially arrive as text, including integers and timestamps. This example shows only the header and first evidence row; the final example below assumes two further matching rows were also available.

06 / SDK cells become named evidence

boundedResults() calls cell()

return boundedResults(
  expected,
  result.ResultSet?.Rows ?? [],
  Boolean(result.NextToken),
  { ...metadata, ok: true },
);
  1. Verify the header's names and order match expected.columns.
  2. Remove the header from the evidence rows.
  3. Determine whether an extra row or next page indicates truncation.
  4. Consider only the first query.limit evidence rows.
  5. Check each row's width and map cell positions to column names.
  6. Call cell(value, type) for every selected value.
  7. Admit only complete rows that fit the serialized 65,536-byte response budget.
  8. Return rows, column types, result count, truncation information, and execution metadata.

The response-size check includes execution metadata, column definitions, and truncation fields, not just the rows. It reserves space for truncation metadata and removes the last candidate row if the complete response would exceed 64 KiB.

This is result formatting, not ETL. The tool does not recalculate severity, change event IDs, or rewrite source data. It selects stored evidence and converts Athena's wire representation into usable objects.

cancel() is already implemented, but separate

Cancellation is not part of the ordinary query_events path. An internal cancel_query request validates its keys and execution ID, uses execution() to check the workgroup, and calls StopQueryExecution only for QUEUED or RUNNING executions. Unknown or finished queries are safe no-ops; a completion race triggers another state/workgroup check.

Cancellation is not a Bedrock-selectable tool or public browser endpoint. The future authenticated Stop API must verify server-side user/turn ownership before invoking it.

What the current slice does and does not do

Built versus deferred

Implemented in the current code

The private query tool

  • Typed request validation and allowlisted SQL compilation.
  • UTC window bounds and date partition predicates.
  • Asynchronous query submission.
  • Execution/workgroup checks and original-query matching.
  • One-page, row-limited, 64 KiB result conversion.
  • Internal cancellation and safe error handling.
  • Catalog description operation, separate from this flow.
  • Least-privilege CDK role and workgroup configuration.
Future application integration

The orchestrator and API

  • Bedrock ConverseStream tool selection and invocation.
  • Retaining original requests and execution IDs.
  • Polling Athena status across Lambda calls.
  • Enforcing the 180-second query deadline.
  • Server-side user/turn-to-query ownership in DynamoDB.
  • Authenticated Stop API and cancellation authorization.
  • Returning evidence to the model and streaming answers.
  • Persisting conversations and investigation state.

Separate data-governance prerequisite: Lake Formation registration and database/table grants remain deferred and must be implemented before live data-query validation. Having the Lambda code and IAM role is not proof that authorized end-to-end querying is ready.

The Bedrock model has no AWS identity. The future orchestrator invokes this tool but does not receive Athena or direct security-log S3 access. The query role is limited to its environment's workgroup and results prefix; registered normalized data is intended to be authorized through Lake Formation.

Current guardrails are distinct: the 30-day default caps the requested time range; the 128 MiB cutoff limits bytes scanned; row limits and the 64 KiB response budget limit returned evidence. query_deadline_seconds: 180 is a lifecycle contract for the future caller, not a timeout enforced inside this Lambda.
